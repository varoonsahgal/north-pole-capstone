📜 The brief

Santa was impressed. Then he asked three hard questions:

  1. "Why is the gift list typed into the code?" The elves in Logistics keep the real list in a file. The app should load it from an API.
  2. "Why did it take four elves and three hours to change one word?" Changing the app should be as easy as pushing code. A pipeline should build and deploy it.
  3. "What if we outgrow this?" Mrs. Claus has heard good things about Kubernetes. Show that the same container runs there too.

How this mission is different

  • Goals, not steps. Each goal says what "done" looks like. How you get there is your call.
  • Hints are wrapped. Each goal has hints inside gift boxes, from a gentle nudge to a strong push. Try for ten honest minutes before you unwrap one. Struggling a little is the point.
  • Field guides exist. If a whole area is new to you, the field guides walk through it with screenshots. They are a safety net, not the route.
  • The Grinch has been busy. Some things will fail on purpose. Each failure is a lesson someone paid for in production.
The elf code still applies

Everything is named [[TEAM]]-something, everything lives in us-west-2, and no access key ever goes into a file. Keep using your Santa's Workshop from Mission 1.

Three habits of teams that finish

Keep a captain's log. For every error: what you saw, what you thought it was, what it really was. Screenshot as you go. Your presentation is built from this log.

Sync every hour. Two minutes, standing up: what works, what is stuck, what is next.

Make it work, then make it code. It is fine to build something by hand first to understand it. Goal 7 is where you turn it into Terraform.

1

Claim your repo

⏱ about 30 min

A pipeline starts with a repository that your team controls. Make your own copy of the Sleigh List and get everyone working from it.

Done when

  • Your team has its own GitHub repository created from the sleigh-list template.
  • All four of you can push to it.
  • It is cloned in your workshop, and a small change (your team name in src/config.js) has been pushed from there.
  • You have agreed who owns which goals.
Nudge: making the copy

On the template's GitHub page there is a green Use this template button. One teammate creates the repository under their own account, then adds the others under Settings → Collaborators.

Hint: pushing from the workshop

GitHub does not accept your account password on the command line. The owner of the repository creates a fine-grained personal access token (GitHub → Settings → Developer settings) limited to this one repository with Contents: read and write, and uses it as the password when git asks. Treat that token like a password: it never goes in a file in the repo.

Hint: avoiding the "who changed my file" problem

Commit small and often, and run git pull before you start work. If two tracks need the same file (it will be buildspec.yml), talk first.

2

Build the gift API

⏱ about 90 min

The real gift list is the file data/wishlist.json in your repository. Put it in S3, and make it available to the world through a web address, with no server to look after.

🌍Browser
→
🚪API GatewayGET /gifts
→
⚡Lambda[[TEAM]]-get-gifts
→
🪣S3 bucketwishlist.json

Done when

  • Opening https://…execute-api.us-west-2.amazonaws.com/prod/gifts in a browser shows the JSON list of eight gifts.
  • The bucket is private. Only the Lambda function can read the file.
  • You can explain what each of the three services contributes.
Fair warning

The gift API field guide gets you most of the way, and it has a deliberate mistake in it. Your Lambda test will pass and your API will still fail. Finding out why is part of this goal.

Nudge: my Lambda says AccessDenied

A new Lambda function may write logs and nothing else. Who is the function, as far as S3 is concerned? Find its execution role and give it permission to get that one object.

Hint: the Lambda test passes but the API returns "Internal server error"

The problem is between Lambda and API Gateway, so look there. In API Gateway, open your GET method and use the Test tab. Read the log it prints, right to the last lines. It names the problem exactly.

Bigger hint: "Malformed Lambda proxy response"

With Lambda proxy integration, API Gateway expects a very particular reply: a statusCode, optional headers, and a body that is a string. Check what type your function's body is. Python has a one-line way to turn a list into a JSON string.

Hint: bucket names

S3 bucket names are unique across all of AWS, not just your account. [[TEAM]]-wishlist is probably taken. Add your account number to the end.

3

Connect the app to the API

⏱ about 30 min

Tell the Sleigh List where the API lives, and see eight gifts instead of four.

Done when

  • The app shows a green box: 📡 Loaded 8 gifts from the North Pole API.
  • You can explain what CORS is to someone who has never heard of it.

There is exactly one line to change, in src/config.js. Test it the way you did in Mission 1: build the image, run it in the workshop, and look at /proxy/3000/.

The app turns red

If the app shows a red box, it is telling you the truth, but not the whole truth. Open your browser's developer tools (F12) and read the Console tab.

Nudge: the API works in a browser tab but not from the app

When you type an address into the address bar, the browser simply fetches it. When JavaScript on one website asks for data from a different website, the browser first checks whether the other site allows it. Your API has not said that it does.

Hint: what the browser wants to see

The reply from your API needs a header called Access-Control-Allow-Origin. With Lambda proxy integration, API Gateway passes through whatever headers your function returns. So the fix is in your Lambda code, in the same dictionary as statusCode.

Hint: I changed config.js and nothing changed

config.js is baked into the image when it is built. Did you rebuild the image and start a new container? Is an old container still holding port 3000 (docker ps)? Did your browser cache the old page (try a private window)?

4

Put your image in ECR

⏱ about 30 min

You have done this before. This time there is no page to copy from: use your memory, your Mission 1 notes, and each other.

Done when

  • Your repository on GitHub contains a Dockerfile that builds the app.
  • An ECR repository named [[TEAM]]-sleigh-list holds an image built from it.
Nudge

Two stages: one that builds, one that serves. The serve stage needs three things copied in: the nginx config, the elf script, and the built site.

Hint: "toomanyrequests: You have reached your pull rate limit"

Docker Hub limits anonymous downloads, and four teams plus a build service share very few IP addresses. Use base images from Amazon's public registry instead: public.ecr.aws/docker/library/node:22-alpine and public.ecr.aws/nginx/nginx:1.27-alpine.

Hint: I forgot the push commands

In the ECR console, open your repository and click View push commands. AWS writes them out for you.

5

Run it on ECS, by hand

⏱ about 60 min

Get your image running on ECS Fargate behind a load balancer, using only the AWS console. No Terraform yet.

Why by hand, when you know Terraform?

Two reasons. The console shows you every option that exists, which is the fastest way to learn what a service can do. And after an hour of clicking, you will never again wonder whether infrastructure as code is worth the effort.

Done when

  • A cluster, task definition and service exist, created in the console, and at least two tasks are running.
  • Your app answers at a load balancer address, and 🔔 Ring the bell shows more than one elf.
  • Your Scribe has a list of every setting you had to choose. You will need it for goal 7.
Nudge: the order of things

The same order as Mission 1: cluster, then task definition, then service. The "create service" screen can create the load balancer, listener and target group for you as part of the same form.

Hint: values people get wrong
  • Container port: 3000, not 80.
  • Health check path on the target group: /health.
  • Public IP for the tasks: turned on. Without it a task in a public subnet cannot reach ECR to download its image.
  • Security groups: the load balancer accepts port 80 from anywhere. The tasks accept port 3000 from the load balancer's group.
Hint: tasks keep stopping

Click a stopped task and read Stopped reason. "CannotPullContainerError" is about reaching ECR (public IP, or the wrong image address). "Task failed ELB health checks" is about the firewall or the health check path. The Grinch field guide has more.

Need the full walk-through? See the Fargate field guide.

6

Build the pipeline

⏱ about 2 hours

This is the heart of the mission. After this goal, nobody on your team runs docker build or docker push by hand again.

🐙git push
→
📥SourceCodePipeline fetches the commit
→
🔨BuildCodeBuild runs buildspec.yml
→
🚀DeployECS rolls out the new image

Done when

  • Someone changes BANNER in src/config.js, commits and pushes.
  • Without anyone touching AWS, the new banner appears at your load balancer address a few minutes later.
  • The build label in the app's footer shows the commit that is running, not the word local.

Think first

  • CodeBuild starts from an empty machine every time. What does it need to be told, and what does it need to be allowed to do?
  • How will the Deploy stage know which image the Build stage just made?
Nudge: the pieces

You need four things: a connection from AWS to GitHub, a CodeBuild project, a buildspec.yml file in your repo that lists the build commands, and a pipeline with three stages that ties them together.

Hint: "Cannot connect to the Docker daemon" in the build log

Building Docker images inside CodeBuild needs extra rights on the build machine. In the project's environment settings, turn on Privileged mode.

Hint: the build fails at "docker push" or at login

CodeBuild runs as an IAM role, and that role starts with almost no permissions. It needs to push to ECR. There is a managed policy made for exactly this: AmazonEC2ContainerRegistryPowerUser.

Hint: Deploy fails, or succeeds but nothing changes

The ECS deploy action reads a small file that your build must produce, called imagedefinitions.json. It contains the container name and the image address. The name must match the container name in your task definition exactly. List the file under artifacts in your buildspec so it is handed to the next stage.

Hint: showing the commit in the app's footer

The Dockerfile accepts a build argument called BUILD_ID. CodeBuild provides the commit in the variable CODEBUILD_RESOLVED_SOURCE_VERSION. Tagging the image with the short commit as well as latest is a good habit: you can always tell what is running.

Hint: the connection says "Pending"

A connection to GitHub has to be approved by a human in the console: select it and choose Update pending connection. The person doing it must be signed in to the GitHub account that owns your repository.

Full walk-throughs: CI/CD pipeline and auto-deploy to Fargate.

7

Turn it into Terraform

⏱ about 2.5 hours

Right now your factory exists because several elves clicked several hundred things. If it vanished tonight, could you rebuild it by morning? Write it down as code, in your repository, in a terraform/ folder.

Done when

  • terraform apply creates the API (bucket, function, gateway), the ECS setup, and the pipeline.
  • The Terraform state lives in an S3 bucket, and two teammates can both run terraform plan against it.
  • Your repository contains no secrets: no access keys, no tokens, no state files.
  • You have proven it: destroy everything, apply again, push a commit, and the app comes back.
Start from what you have

Your Mission 1 files are most of the ECS part. Copy them into terraform/ and build from there. Add one area at a time and apply after each. Do not write 400 lines and apply once.

Think first

  • If two people run terraform apply at the same moment from two copies of the state, what happens?
  • The console-built resources from goals 2, 5 and 6 already use your names. What are your options?
  • Your pipeline now changes the ECS service on every push. Terraform also manages that service. Who wins?
Nudge: shared state

Look up Terraform's backend "s3" block. The state bucket has to exist before Terraform can use it, so create that one bucket by hand (turn on versioning). Recent Terraform versions can lock the state using S3 alone with use_lockfile = true.

Hint: "already exists" errors

Terraform will not adopt something it did not create. The simplest path: delete the hand-built version, then let Terraform create it. (You wrote down your settings in goal 5, so you know what to put in the code.) The advanced path is terraform import.

Hint: every apply rolls my app back to an old version

The pipeline registers a new task definition on each deploy. Terraform sees that the service no longer uses "its" task definition and puts it back. Tell Terraform that this one attribute is no longer its business: look up lifecycle and ignore_changes.

Hint: keeping secrets out

The best secret is one that does not exist. Your workshop and your build project use IAM roles, so there are no AWS keys to hide. Add *.tfstate* and .terraform/ to .gitignore before your first commit, because state files can contain sensitive values. If you ever do need a real secret, such as a database password, keep it in AWS Secrets Manager and let Terraform read it from there.

Hint: the GitHub connection in Terraform

Terraform can create the connection (aws_codeconnections_connection), but it is always born Pending. A human still has to approve it once in the console. That is by design: code should not be able to grant itself access to your GitHub account.

Full walk-through: Terraform for teams.

8

A second home on Kubernetes

⏱ about 2 hours

Run the same image on Amazon EKS. Normally you would never deploy one app to two orchestrators. You are doing it here to see what is the same and what is different.

Read this before you create a cluster

One cluster per team, created by one person. By default eksctl builds a brand-new network for every cluster, and the account does not have room for four of those. Use the command in the EKS field guide, which places your cluster in the existing default network. Creation takes about 15 minutes, so start it early and work on something else while it runs.

Done when

  • kubectl get nodes shows two nodes that are Ready.
  • Three pods of your app are running, created from a deployment.yaml that is in your repository.
  • Your app answers at a second load balancer address, and the footer says on Kubernetes.

Think first

Fill in this table as a team. It makes a great slide.

IdeaECS wordKubernetes word
The recipe for running a containerTask definition?
"Keep 3 copies running"Service?
A stable address in front of the copiesLoad balancer + target group?
"Are you alive?"Target group health check?
Nudge: two files

You need a Deployment (which image, how many copies, which port) and a Service (how to reach them). Put both in a k8s/ folder and apply them with kubectl apply -f k8s/.

Hint: getting a public address

A Service of type: LoadBalancer asks AWS for a load balancer. Its port is what the world uses (80). Its targetPort is what your container listens on (you know this number). The address appears under EXTERNAL-IP in kubectl get service and needs a minute or two to start answering.

Hint: pods stuck in ImagePullBackOff or Pending

Run kubectl describe pod <name> and read the Events at the bottom. ImagePullBackOff is nearly always a typo in the image address. Use the full ECR address including the tag.

Hint: the EKS console says "Error loading resources"

Being an AWS administrator does not make you a Kubernetes administrator. The cluster only knows the identity that created it, which was your workshop's role. Your personal console user is a stranger to it. Look up EKS access entries to introduce yourself. Until then, kubectl from the workshop works fine.

9

One push, two homes

⏱ about 90 min

Extend your pipeline so that the same push that updates ECS also rolls out to your Kubernetes cluster.

Done when

  • You change the banner, push once, and both addresses show the new banner and the same build label.

Think first

  • Your deployment.yaml names an image. Every build produces a new tag. How will the file keep up?
  • In goal 8 the console could not see inside your cluster. Who is running kubectl now, and does the cluster know them?
Nudge: where the commands go

CodeBuild can run kubectl. The standard build image already includes it. Add the Kubernetes steps to the end of your buildspec, after the image is pushed.

Hint: "error: You must be logged in to the server" or "Unauthorized"

Two separate locks. First, the build role needs the IAM permission eks:DescribeCluster so that aws eks update-kubeconfig can find the cluster. Second, the cluster itself must be told to trust that role: create an access entry for the CodeBuild role and associate a cluster access policy with it.

Hint: making the manifest follow the build

One simple way: put a placeholder word in deployment.yaml where the image goes, and have the build replace it with the real address using sed before piping the result to kubectl apply -f -. Finish with kubectl rollout status so the build fails if the rollout fails.

Full walk-through: EKS field guide.

🌟 Gold star challenges

Finished early? These are optional and get no hints. Pick the one that scares you most.

  • Terraform from the pipeline. Add a stage that runs terraform apply, so infrastructure changes are delivered the same way as app changes. What should require a human approval?
  • Your own build image. Installing tools on every build wastes a minute or two. Create a custom CodeBuild image with Terraform already inside, store it in ECR, and use it.
  • A proper front door for Kubernetes. Replace the simple load balancer with an Ingress and the AWS Load Balancer Controller.
  • The cluster as code. Describe your EKS cluster in Terraform instead of creating it with eksctl.
  • Elves on demand. Add autoscaling to the ECS service or the Kubernetes deployment, then prove that it works.
  • Write, not just read. Make the app save a new gift: a second API method, a second Lambda function, and somewhere to store it.
