Open Santa's Workshop

⏱ 15 min

You need one shared computer in the cloud where the whole team can write code and run Docker and Terraform. We call it Santa's Workshop: VS Code running in your browser, on an EC2 server that belongs to your team.

Where did Cloud9 go?

AWS has retired Cloud9 for new customers. The workshop does the same job with the same editor you may already know (VS Code), and everything is pre-installed.

Only the Driver does this step. Everyone else watches the shared screen.

  1. Sign in to the AWS console and check that the region in the top right says United States (Oregon), also known as us-west-2.
  2. Click the CloudShell icon in the top bar (it looks like a small terminal: >_). A terminal opens at the bottom of the page. Close the welcome message if you see one.
  3. Paste this one command and press Enter: curl -fsSL https://varoonsahgal.github.io/north-pole-capstone/workshop/launch.sh | bash -s -- [[TEAM]]
  4. It takes about 8 minutes. Keep the tab open. Use the time for the elf check below.
  5. When it finishes it prints a URL and a password. Paste both into your team chat so all four of you have them.
============================================================ Santa's Workshop is ready for team: [[TEAM]] ============================================================ URL: https://d1234abcd.cloudfront.net/?folder=/home/ec2-user/workshop Password: (20 letters and numbers)

Elf check · while you wait

The command you just ran did not ask for an access key. How was CloudShell allowed to create things in AWS?

Right. CloudShell acts as you, with temporary credentials, for as long as you are signed in. Your workshop does something similar: its server carries an IAM role, so Terraform will never need a key either.

Step inside

  1. Everyone opens the URL and types the password.
  2. You should all see the same folder, with a file called WELCOME.md.
  3. The Driver opens a terminal: click the ☰ menu in the top left, then Terminal, then New Terminal.
  4. Check that the tools are ready: echo "Team: $TEAM" aws sts get-caller-identity --query Arn --output text terraform version docker --version
One keyboard at a time

You all see the same files, but this is not Google Docs. If two people edit the same file at once, the last save wins. Let the Driver type. Everyone else can open their own terminal to look around.

3

Wrap it in a container

⏱ 25 min

A container image is a sealed box holding your app and everything it needs to run. If the box runs in your workshop, it will run the same way on AWS. A Dockerfile is the recipe for building that box.

Two stages: a workshop and a sleigh

Building a React app needs Node.js and hundreds of megabytes of tools. Serving the finished site needs only a few small files and a web server. So the recipe has two stages. Stage 1 builds the site. Stage 2 starts fresh and copies in only the finished files. The big tools are left behind, and the image you ship is small and has less in it to attack.

  1. In the file list, right-click the sleigh-list folder and choose New File…. Name it exactly Dockerfile (capital D, no extension).
  2. Paste this in. Have the Navigator read the comments aloud:
  3. Build the image. The dot at the end means "use the recipe in this folder". cd ~/workshop/sleigh-list docker build -t sleigh-list .
  4. Look at what you made: docker images sleigh-list It should be about 50 MB. The Node.js image you built with is over 150 MB, and none of it shipped.

Test flight

Run a container from your image, right here in the workshop.

docker run -d --name sleigh-test -p 3000:3000 sleigh-list docker ps curl localhost:3000/health curl localhost:3000/elf.json

The first curl should answer ok. The second shows the name of the container that answered.

Now see it. Take your workshop address, remove everything after .cloudfront.net, and add /proxy/3000/. For example: https://d1234abcd.cloudfront.net/proxy/3000/

What does -p 3000:3000 mean?

A container has its own private network. -p 3000:3000 connects port 3000 on the workshop server to port 3000 inside the container. Remember the number 3000. You will need it three more times today.

Stop and remove the test container. You are done with it.

docker rm -f sleigh-test

Elf check

Why does the Dockerfile copy package.json and run npm ci before copying the rest of the code?

Docker saves each step as a layer and reuses it if its inputs did not change. Dependencies change rarely; code changes all the time. Ordering it this way turns a one-minute rebuild into a few seconds. Try it: run the build command again and watch for the word CACHED.

First Terraform: a registry

⏱ 15 min

Your image exists only inside the workshop. AWS cannot run what it cannot reach. You need a registry: a place in the cloud to store images. On AWS that is ECR (Elastic Container Registry).

You could click through the console to make one. Instead you will describe it in code and let Terraform create it. Infrastructure written as code can be reviewed, repeated, and destroyed cleanly.

  1. Make a folder for your infrastructure code, next to the app: mkdir -p ~/workshop/infra cd ~/workshop/infra
  2. In the file list, create main.tf inside infra:
  3. Create terraform.tfvars. This is where the value of the team variable comes from: team = "[[TEAM]]"
  4. Create ecr.tf:
Look for what is NOT there

The provider "aws" block has no access key and no secret key. Terraform automatically uses the IAM role attached to your workshop server. A key that does not exist cannot leak.

The three commands you will use all day

terraform init

init downloads the AWS plugin. You run it once per folder.

terraform plan

plan changes nothing. It shows what Terraform would do. Read it together: one resource to add, marked with a green +.

terraform apply

apply shows the plan again and waits. Type yes to go ahead.

Apply complete! Resources: 1 added, 0 changed, 0 destroyed. Outputs: ecr_repository_url = "123456789012.dkr.ecr.us-west-2.amazonaws.com/[[TEAM]]-sleigh-list"

Scout: open ECR in the console and find [[TEAM]]-sleigh-list. It is empty for now.

How does Terraform remember what it built?

Look in the infra folder. There is a new file, terraform.tfstate. That is Terraform's memory: a list of everything it created. Never edit it by hand, and never delete it while your resources exist. (In Mission 2 you will move it somewhere safer.)

5

Ship the image to ECR

⏱ 10 min

Pushing an image takes three moves: sign Docker in to your registry, give the image its full address as a name, and push.

cd ~/workshop/infra # 1. Ask Terraform for the repository address and remember it REPO=$(terraform output -raw ecr_repository_url) echo $REPO # 2. Sign Docker in to ECR (the password is temporary and never shown) aws ecr get-login-password | docker login --username AWS --password-stdin ${REPO%%/*} # 3. Give the image its full registry name, then push it docker tag sleigh-list:latest $REPO:latest docker push $REPO:latest

You should see Login Succeeded, then several layers being pushed.

Scout: refresh the repository in the console. There is your image, tagged latest, about 21 MB compressed.

It says "no basic auth credentials" or "denied"

The login step did not work, or you opened a new terminal where $REPO is empty. Run all of the commands above again, in the same terminal, from the top.

A cluster and a task

⏱ 20 min

ECS (Elastic Container Service) runs containers for you. It has three ideas, and you will build them in order:

🏘️Clustera named home for your containers
+
📋Task definitionthe recipe: which image, how much CPU, which port
+
👷Service"keep 3 of these running, always"

You will use the Fargate flavour of ECS. With Fargate there are no servers for you to manage. You say what to run, and AWS finds somewhere to run it.

The cluster

Create cluster.tf in infra:

The task definition

This file has three parts. Create task.tf, then read the notes below it.

PartIn plain words
The roleECS has to pull your image from ECR and write logs for you. It needs your permission to do that. The role says "the ECS tasks service may act with these rights", and the attached policy lists the rights.
The log groupAnything your container prints goes here, in CloudWatch. When a container will not start, this is the first place to look.
The task definitionWhich image to run, how big (a quarter of a CPU and 512 MB), and which port the container listens on. There is that 3000 again.
Terraform connects the dots for you

Find this line: image = "${aws_ecr_repository.app.repository_url}:latest". You never typed the repository address. Terraform reads it from the resource you made in step 4. This also tells Terraform the order: registry first, task definition second.

Plan, read, then apply:

cd ~/workshop/infra terraform plan terraform apply

Expect Resources: 5 added. Scout: open ECS in the console. Find [[TEAM]]-cluster under Clusters and [[TEAM]]-sleigh-list under Task definitions.

Elf check

You have a cluster and a task definition. How many containers are running right now?

Zero. A task definition is only a recipe, and a cluster is only an empty home. Nothing runs until something asks for it. That something is the service, which you build next.

7

The service: keep three running

⏱ 20 min

A service is a promise: "keep this many copies of the task running". If one dies, the service starts a replacement without anyone waking up.

Create service.tf with the smallest service that could possibly work:

# The service keeps 3 copies of our task running at all times resource "aws_ecs_service" "app" { name = "${var.team}-service" cluster = aws_ecs_cluster.main.id task_definition = aws_ecs_task_definition.app.arn launch_type = "FARGATE" desired_count = 3 } terraform apply
The Grinch says hello

The plan looks fine, you type yes, and then:

Error: creating ECS Service ([[TEAM]]-service): ... InvalidParameterException: Network Configuration must be provided when networkMode 'awsvpc' is specified.

This is your first real cloud error. Read it slowly before you scroll on. It tells you exactly what is missing.

In the task definition you chose network_mode = "awsvpc". That gives every task its own network card. A network card has to be plugged in somewhere, and you have not said where. The service needs to know which subnets to use.

Your account already has a default network (a VPC) with one public subnet in each availability zone. You only need to look them up. Create network.tf:

resource makes things. data looks things up.

Four teams share this network. Because you used data blocks, Terraform will only ever read it. Nobody's terraform destroy can delete the network out from under another team.

Now replace everything in service.tf with this version. The new part is the network_configuration block:

terraform apply

Scout: in the ECS console open [[TEAM]]-cluster, then [[TEAM]]-service, then the Tasks tab. Within a minute, three tasks go from Provisioning to Running.

Try to visit one

Click a running task. Under Configuration it has a public IP. Try opening http://that-ip:3000 in your browser. It will hang and time out. The container is running, but a firewall is in the way. Even if you got through, you would have three different addresses that change every time a task restarts. You need one stable front door.

8

The front door

⏱ 35 min

An Application Load Balancer (ALB) gives you one public address and spreads visitors across your healthy containers. It has four parts, and the Grinch has hidden a trap between each of them. That is on purpose: you will learn each part by seeing what breaks without it.

🌍Browser
→
👂Listener"I answer port 80"
→
📇Target groupthe list of healthy containers
→
🧝Tasksport 3000

Part A · The load balancer and its firewall

Create loadbalancer.tf. A security group is a firewall. This one lets the whole internet reach the load balancer on port 80 (plain web traffic).

terraform apply

Load balancers take two to three minutes to create. Do the elf check while you wait.

Elf check · while you wait

Your three tasks are spread across three availability zones (separate data centres). Why does that matter on Christmas Eve?

Exactly. The old server under the stairs was a single point of failure. Three zones means a whole building can lose power and the Sleigh List stays up.

When the apply finishes it prints an app_url. Open it in a new browser tab.

Trap 1: nobody is listening

The browser says it cannot connect. The load balancer exists, but you have not told it to listen on any port, or where to send people. An ALB with no listener is a door with no doorbell.

Part B · A listener and a target group

Create targets.tf:

The target group is an empty list until your service signs its tasks up. Tell the service to do that. Replace everything in service.tf. The new part is the load_balancer block:

terraform apply

Wait one minute, then refresh the app URL.

Trap 2: 503, then 504

Now the load balancer answers, but with an error page: 503 Service Temporarily Unavailable or 504 Gateway Time-out. That is progress. The door opens, but there is nobody healthy behind it.

Scout, this one is yours. In the console go to EC2 → Target groups, open [[TEAM]]-tg, and look at the Targets tab.

Stop and talk about it for two minutes before opening the hints. The health check is a request from the load balancer to each task on port 3000. It "timed out". What could stand between the load balancer and a task?

Hint 1

"Timed out" is different from "refused". Refused means something answered "no". Timed out means the request vanished and nothing answered at all. What kind of thing silently drops network traffic?

Hint 2

A firewall. You gave the load balancer a security group. Which security group did you give the tasks? Look at network_configuration in service.tf.

The answer

You never chose a security group for the tasks, so AWS gave them the network's default one. That group only accepts traffic from other members of itself. The load balancer is not a member, so its health checks are dropped. It is the same firewall that stopped you visiting a task directly in step 7.

Part C · Let the load balancer in, and only the load balancer

Replace everything in service.tf one last time. There is a new security group at the top, and one new line inside network_configuration.

The best line in this whole mission

Look at security_groups = [aws_security_group.alb.id] inside the ingress block. The source is not a list of IP addresses. It is another security group. It means: "accept port 3000 only from things that wear the load balancer's badge". The internet cannot reach your containers directly at all. Everything must come through the front door.

terraform apply

Changing the firewall makes ECS replace all three tasks, one batch at a time. This takes three to four minutes. Scout: keep refreshing the Targets tab and call out when all three say Healthy.

Now refresh your app URL. If you closed it:

terraform output app_url
You did it

That address works for anyone, anywhere. Three containers, three data centres, one front door, all written as code.

My browser shows a security warning or cannot connect

Your address starts with http://, not https://. Some browsers switch to https by themselves, and you have no listener on port 443. Type the full address including http://. (Adding real HTTPS needs a domain name and a certificate. It is a good stretch goal for Mission 2.)

9

Victory lap

⏱ 10 min

You built it. Now prove to yourselves that it does what you promised Santa.

1. Meet your elves

At the bottom of your app, click 🔔 Ring the bell a few times. The elf name and the zone change. Each click is a new request, and the load balancer hands each one to a different container. That is load balancing, and you can see it.

2. Lose an elf

Stop one task on purpose, and watch the service replace it. Keep the app open in another tab and keep ringing the bell while you do it.

# Pick one running task and stop it TASK=$(aws ecs list-tasks --cluster $TEAM-cluster --query 'taskArns[0]' --output text) aws ecs stop-task --cluster $TEAM-cluster --task $TASK --query 'task.lastStatus' --output text # Watch the service notice and start a replacement (press Ctrl+C to stop watching) watch -n 5 "aws ecs describe-services --cluster $TEAM-cluster --services $TEAM-service --query 'services[0].[desiredCount,runningCount,pendingCount]' --output text"

The three numbers are wanted, running and starting. You will see 3 2 1, then 3 3 0. The app never went down. Nobody was paged.

3. Hire more elves

Christmas Eve is coming. In service.tf, change desired_count = 3 to desired_count = 5, then:

cd ~/workshop/infra terraform plan

Read the plan. One resource changes, marked with a yellow ~, and Terraform shows 3 -> 5. Nothing is destroyed. Apply it and ring the bell until you have met five elves.

terraform apply

Final elf check

A teammate opens the console and changes the service to 2 tasks by hand. What happens the next time someone runs terraform plan?

Terraform compares your code with what really exists. Your code is the truth, and Terraform will pull reality back to match it. This is why teams agree: if it was made with Terraform, change it with Terraform.
