Terraform for Teams

In Mission 1 one Driver ran Terraform from one folder. Now four of you share one set of infrastructure. Three things have to change.

{{hills}}

What changes when a team shares Terraform

ProblemWhat goes wrongThe fix
State on one machineA teammate applies from their own copy. Terraform thinks nothing exists and tries to create everything a second time.Keep the state in S3, with locking
Secrets in filesA key is committed to GitHub and found by a bot within minutes.Use roles, and keep state out of git

This guide gives you the patterns and the awkward parts. It does not give you the whole configuration. Writing that is the goal.

1

Lay out the repository

Keep the infrastructure code next to the app it runs. One suggested layout:

sleigh-list/ ├── src/ the app ├── Dockerfile ├── buildspec.yml ├── data/wishlist.json ├── lambda/ │ └── lambda_function.py ├── k8s/ deployment.yaml, service.yaml └── terraform/ ├── main.tf provider, backend ├── variables.tf ├── terraform.tfvars team = "[[TEAM]]" (no secrets in here!) ├── api.tf bucket, function, API Gateway ├── ecs.tf everything from Mission 1 └── cicd.tf connection, CodeBuild, CodePipeline

Before the first commit, make sure .gitignore contains these lines:

.terraform/ *.tfstate *.tfstate.*
2

Move the state to S3

The state bucket is the one thing Terraform cannot create for itself, because it needs somewhere to keep state before it can create anything. Make it by hand, once:

ACCOUNT=$(aws sts get-caller-identity --query Account --output text) aws s3 mb s3://$TEAM-tfstate-$ACCOUNT aws s3api put-bucket-versioning --bucket $TEAM-tfstate-$ACCOUNT \ --versioning-configuration Status=Enabled

Versioning keeps every old copy of the state. If a state file is ever damaged, you can go back.

Then tell Terraform to use it. Add a backend block inside the terraform block in main.tf:

terraform { required_version = ">= 1.10" required_providers { aws = { source = "hashicorp/aws" version = "~> 6.0" } } # Remote state: the team shares ONE state file, stored in S3. backend "s3" { key = "capstone-2/terraform.tfstate" region = "us-west-2" use_lockfile = true # S3-native locking: two people cannot apply at the same time } } provider "aws" { region = "us-west-2" default_tags { tags = { Team = var.team Project = "capstone-2" } } }

The bucket name is not in the file, because a backend block cannot use variables. Pass it when you initialize:

cd terraform terraform init -backend-config="bucket=$TEAM-tfstate-$ACCOUNT"

From now on, anyone on the team who clones the repository and runs that same init is working with the same state. Run terraform plan from two terminals to prove it.

What is the lock for?

While one person is applying, Terraform writes a small lock file next to the state. Anyone else who tries gets Error acquiring the state lock and has to wait. Without it, two applies at once can leave the state describing something that does not exist. If a lock is left behind after a crash, terraform force-unlock removes it. Ask the team first.

Default tags. The default_tags block stamps every resource with your team name. It makes cleanup and cost reports much easier.

4

The awkward parts

Every team meets these. Here is what each one is about.

API Gateway does not redeploy by itself

In the console you clicked Deploy API after each change. Terraform needs a reason to do the same. Give the deployment a triggers block that changes whenever the API changes:

resource "aws_api_gateway_deployment" "gifts" { rest_api_id = aws_api_gateway_rest_api.gifts.id # Redeploy whenever the method or integration changes triggers = { redeploy = sha1(jsonencode([ aws_api_gateway_resource.gifts.id, aws_api_gateway_method.get.id, aws_api_gateway_integration.lambda.id, ])) } lifecycle { create_before_destroy = true } }

API Gateway needs permission to call Lambda

The console added this for you without saying so. In Terraform you must write it: an aws_lambda_permission that allows the principal apigateway.amazonaws.com to invoke your function. Without it the API returns "Internal server error" and the function's logs are empty, because the function was never called.

One more detail: API Gateway always calls Lambda with POST, even for a GET method. So the integration has integration_http_method = "POST" and type = "AWS_PROXY".

The pipeline and Terraform both manage the ECS service

Each deploy registers a new task definition and points the service at it. Terraform then sees a difference and wants to point the service back at the old one. Tell it to stop caring about that one attribute:

# The pipeline registers new task definition revisions on every deploy. # Without this, the next "terraform apply" would roll the service BACK to the old image. lifecycle { ignore_changes = [task_definition] }

The first apply happens before any image exists

Terraform creates an empty ECR repository and a service that wants an image from it. For the first few minutes the tasks will fail to start. That is expected. Once the pipeline's first run pushes an image and deploys it, everything settles.

The GitHub connection is created Pending

Terraform can create the connection, but a person has to approve it once in the console (Developer Tools → Settings → Connections → Update pending connection). After that, choose Release change on the pipeline to start the first run.

Names that already exist

If you built things by hand in goals 2, 5 and 6 with the same names, Terraform will report that they already exist. The simplest approach is to delete the hand-built ones first. Bucket names in particular must be unique, so the hand-built bucket has to go before Terraform can create its own.

5

Secrets

The safest secret is one that does not exist. Look at how much of this project needs no secret at all:

Who needs AWS accessHow it gets itKeys stored anywhere?
Terraform in your workshopThe server's IAM roleNone
CodeBuildThe build project's IAM roleNone
The Lambda functionIts execution roleNone
ECS tasksThe task execution roleNone
AWS reading GitHubThe connection you approvedNone

Rules for the day you do have a secret

  • Never write it in a .tf or .tfvars file that goes to git, and never put an access_key in a provider block.
  • Store it in AWS Secrets Manager or SSM Parameter Store, and let Terraform or the application read it from there at run time.
  • Mark sensitive variables and outputs with sensitive = true so Terraform does not print them.
  • Remember that the state file can contain secret values in plain text. That is one more reason it lives in a private bucket and not in git.
Example: reading a secret without ever writing it down
# Someone created this secret by hand in Secrets Manager. Terraform only reads it. data "aws_secretsmanager_secret_version" "db" { secret_id = "${var.team}/database-password" } # Use it where it is needed. The value never appears in your code or in git. # password = data.aws_secretsmanager_secret_version.db.secret_string
If a key ever does reach GitHub

Deleting the commit is not enough. Bots copy keys within minutes, and git history keeps them. Deactivate the key in IAM straight away, then tell your instructor.

6

The real test

You only know your code is complete when it can rebuild everything from nothing.

  1. terraform destroy
  2. terraform apply
  3. Approve the connection in the console and choose Release change.
  4. Put the new API address in src/config.js and push. (The address changes when the API is recreated. How could you avoid that step? A good question for your presentation.)
  5. Open the app. Eight gifts, loaded from the API, delivered by the pipeline.

If that works, your whole factory is a folder of text files. You can review it, copy it for a second environment, or rebuild it after a disaster.
