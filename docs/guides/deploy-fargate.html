Field guide · Mission 2, goals 5 and 6

Deploy to Fargate

First get the app running on ECS by hand. Then add a Deploy stage so the pipeline rolls out every new image.

Part 1 · ECS in the console

You built exactly this with Terraform in Mission 1. Doing it by hand shows you the same pieces from the other side. Have your Scribe write down every value you choose. You will type them into Terraform later.

Before you start: an image in your ECR repository [[TEAM]]-sleigh-list. Copy its URI from the ECR console.

The console changes often. Use the field names here as a guide, not as exact labels.

  2. Cluster name: [[TEAM]]-cluster.
  3. Infrastructure: AWS Fargate (serverless) only. Create.

The two classic mistakes

Public IP off. The tasks start, cannot reach ECR to download the image, and stop with CannotPullContainerError.

Health check path left as / with the wrong port, or a firewall that does not allow the load balancer through. The tasks run but are marked unhealthy and replaced, again and again.

Check it

  • Service → Tasks: three tasks, Running.
  • Service → Health and metrics: the target group shows healthy targets.
  • Open the load balancer's DNS name (EC2 → Load balancers) with http:// in front.
Tighten the firewall (recommended)

The wizard's new security group may allow port 3000 from anywhere. Edit [[TEAM]]-tasks-sg so the source of the port 3000 rule is the load balancer's security group rather than 0.0.0.0/0. Then only the load balancer can reach your containers, as in Mission 1.

4

Tell the Deploy stage which image to use

The ECS deploy action needs a small file from the build, named imagedefinitions.json, that says "put this image in the container named this". Add two things to your buildspec.yml: one more command at the end of post_build, and an artifacts section at the bottom.

buildspec.yml (the end of the file)
  post_build:
    commands:
      - docker push $REPO_URI:$IMAGE_TAG
      - docker push $REPO_URI:latest
      # The ECS deploy stage reads this file to learn which image to roll out
      - printf '[{"name":"%s","imageUri":"%s"}]' "$CONTAINER_NAME" "$REPO_URI:$IMAGE_TAG" > imagedefinitions.json

artifacts:
  files:
    - imagedefinitions.json

CONTAINER_NAME must be exactly the container name in your task definition (sleigh-list). If the names differ, the deploy fails and says the container was not found.

Do not push yet. Add the stage first.

5

Add the Deploy stage

  1. Open your pipeline and choose Edit.
  2. Below the Build stage choose Add stage. Name it Deploy.
  3. In the new stage choose Add action group:
    • Action name: ECS
    • Action provider: Amazon ECS
    • Input artifacts: BuildArtifact
    • Cluster name: [[TEAM]]-cluster
    • Service name: [[TEAM]]-service
    • Image definitions file: imagedefinitions.json
  4. Choose Done, then Save the pipeline.

Now commit and push your buildspec change.

The Deploy stage fails with an access error

The pipeline's service role needs to update ECS and to pass the task execution role to it. When the console creates the role it usually includes this. If yours does not, add the ECS permissions and iam:PassRole to the pipeline's role in IAM.

6

Prove it

  1. Open your app and note the build label in the footer.
  2. Change BANNER in src/config.js, commit and push.
  3. Watch all three stages go green.
  4. Reload the app: new banner, new build label.

That is continuous delivery. A change travels from a keyboard to production in about four minutes, the same way every time.

Watch a rolling update happen

During a deploy, keep clicking 🔔 Ring the bell. For a minute you will see elves on the old build and elves on the new build answering side by side. ECS starts new tasks, waits for them to be healthy, and only then stops the old ones. Visitors never see an outage.
